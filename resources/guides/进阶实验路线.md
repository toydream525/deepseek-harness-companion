# 稳定基线完成后的进阶实验

先完成《从零配置指南》的十项本机验收，再逐项尝试。这里是**条件式路线**，不是 DSH 伴航当前版本已经内置、启用或在新机器验证的承诺。第三方引擎、编译工具、模型、模板与插件由用户自行按各项目说明取得；不要覆盖正常运行的目录或让实验配置自动启动。

## 1. 64K，然后 Adaptive KV Streaming

先在普通主线 llama.cpp 与 Huihui IQ3_S 上从已通过的 32K 升到 64K。原目标硬件曾记录 64K、48 GPU 层、K/V q8_0、batch/ubatch 256、Flash Attention 开、并发 1，但新机必须重新观察 RAM、VRAM、首字耗时、prompt 与 decode 速度、文档中段/尾段检索、思考和工具调用。64K 不稳定就不要继续。

128K 及以上可评估 [Adaptive KV Streaming 项目](https://github.com/RaymondHuang210129/llama.cpp-adaptive-kv-streaming)。其 README 称当前分支为实验性 CUDA `llama-server`，项目主要在另一张 16 GB 卡与另一量化上验证；不能把作者的性能图当作 i7-13700K/RTX 4080/IQ3_S 的数据。源码目录、构建产物目录与主线引擎分别保存，勿混合 DLL。按该项目当前 README 安装 C++ 编译器、CMake 与 CUDA Toolkit 后**另行编译**；这条源码构建路线与普通预编译 CUDA 包“通常无需完整 Toolkit”不同。先运行实验版 `llama-server.exe --help`，确认当前选项及支持的 KV 类型，再在伴航「运行环境」选取实验版引擎。旧启动脚本不是新分支的参数依据。

关键开关是 `--kv-stream-arena-mib`；项目说明旧 `--kv-stream-stage-mib` 只是兼容别名。Arena 是 CUDA 中共享的物理分配，覆盖 resident KV、传输环以及 prefill/decode 阶段计算工作区，**不是单纯 KV 池**。2304 MiB 只是旧例。对原 RTX 4080 16 GB，可把 1024、1536、2048、2304、2560 MiB 当作待测候选，实际值由项目当前 [benchmark/probe 说明](https://github.com/RaymondHuang210129/llama.cpp-adaptive-kv-streaming/blob/feature/kv-stream-phase-arena/benchmarks/README.md)及 OOM、峰值显存、prefill/decode 表现决定。模型、batch、GPU 和其他显存占用都会改变结果。项目 README 的示例 K q8_0 / V q4_0 与旧稳定档 K/V q8_0 **不同**，不可未经测试直接替换。

`--cache-ram` 是 llama-server 的主机 RAM prompt/prefix cache 上限，不是给 Adaptive KV Streaming 分配同样大小的 host KV。旧目标机器 64 GB RAM 可把 8192、16384 作为候选，但必须看系统总内存与实际压力。普通参数预设 schema 当前没有 arena、cache-ram 或实验引擎专属字段；若界面尚不能单独配置，须以该实验引擎官方命令行/独立实验配置进行，不得把未传入的参数写成“已生效”。

顺序是 32K → 64K → 128K → 200K → 262144。每一级需完成长文档中段/尾段检索、Agent 多轮、reasoning、tool call/result 闭环，再进入下一级。262K 的标称 GGUF 上下文不会自动意味着成功。原提示词的极限档框架为 262144 上下文、K/V q8_0、Flash Attention、并发 1、batch/ubatch 256、`--cache-ram 16384`、实测 arena；所有开关需以**当前实验运行器** `--help` 与内存测试为准，MTP 先关闭。

## 2. MTP A/B

MTP 用于尝试提高 decode 速度，默认主力保持关闭。只有中文、代码、思考、工具结果回传、多轮 Agent、32K/64K 已稳定后，才以独立运行档尝试。原提示词建议先确认运行器支持 `--spec-type draft-mtp` 和 `--spec-draft-n-max 2`，不要从 4 起步，也不要在写作 IQ4_XS/16 GB 显存紧张档默认开启。固定同一道题与采样、模型、模板、上下文，记录 MTP OFF/ON 的 decode tok/s、接受率、TTFT、RAM/VRAM 峰值、重复任务、工具 JSON、代码与长任务质量。只有速度显著改善且接受率、质量都可接受，才考虑日常启用。当前普通预设 JSON 无 MTP 字段，绝不因选择示例预设而开启。

## 3. 视觉

先完成文本、reasoning、tool call 与 Agent 基线。选择和当前 Qwen3.8-27B GGUF 明确匹配的 mmproj；不要用旧 Qwen3.5 投影器。原环境的 `mmproj-model-bf16.gguf` GGUF 头为 `clip`、BF16，约 931 MB；只用这条证据还不能证明它和任意新下载的模型相配，必须按模型仓库核对。原方案通过 `--no-mmproj-offload` 把视觉投影主要放在 CPU/RAM 来节省 VRAM，前提是当前引擎支持。先用 720P 再用 1080P 图片，分别记录 OCR/描述正确性、耗时、RAM/VRAM。当前主力文本档不需要视觉文件。

## 4. Compaction 与可选引擎

伪长上下文/compaction 放在最后。备选项目为 [DSH compaction 插件](https://github.com/TsFreddie/dsh-compaction-instant)，或者 [oh-my-pi](https://github.com/can1357/oh-my-pi) + [pi-vcc](https://github.com/sting8k/pi-vcc)。安装前查当前 README、发行版本、DSH/插件兼容性及已知问题；在独立 DSH profile 中实验，保留可恢复的正常 profile。compaction 不能替代 32K/64K 的真实模型和工具测试。Atomic TurboQuant 不是基线必要组件；若专门研究 turbo3/turbo4，另存独立目录、独立引擎，不覆盖主线或 KV Streaming。

## 5. 实验记录与结论

每次记录日期、硬件、驱动、模型仓库与 GGUF 文件/大小、引擎 commit、模板版本/commit、上下文、K/V KV 类型、batch/ubatch、Flash Attention、GPU 层、arena、cache-ram、reasoning effort/budget、请求 max_tokens、MTP 状态/接受率、prompt/decode tok/s、TTFT、峰值 RAM/VRAM、OOM、CPU offload、输出质量与 tool result 后续结果。分清“本机已实测”“旧机记录”“项目作者报告”和“计划未测”。未成功的阶段同样记录失败原因与上一级稳定档。
