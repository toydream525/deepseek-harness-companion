# DSH 伴航：从空电脑配置本地 Qwen 与 DeepSeek Harness

本指南适用于已解压 DSH 伴航、尚无模型、推理引擎或 DSH 的 Windows 电脑。程序本身不附带模型权重、llama.cpp、Node.js 或 DSH，也不会暗中安装它们。按下面顺序下载、选择路径、验证，完成后可在伴航中启停模型、试聊、接入 DSH 和按需开放带密钥的局域网 API。若已经有可用文件，可以复制到另一独立目录并从第 2 步开始。旧 Qwen3.5 清理属于原部署时的一次性任务，本次新配置无需重复清理。

## 五分钟路线图

1. 在「设置与诊断 → 运行环境」查看设备，打开 [llama.cpp 官方 Releases](https://github.com/ggml-org/llama.cpp/releases)，下载 Windows x64 CPU 版，完整解压。NVIDIA 用户可选适合驱动的 CUDA 版并按发行页说明取得配套运行库；其他 GPU 先核对发行页与驱动支持。选择解压目录中的 `llama-server.exe`，点「检测并使用」。
2. 在「模型库与下载」打开下文列出的 Hugging Face 仓库，挑选**明确的 GGUF 文件及量化**；下载后导入。先选单文件模型。若是 `-00001-of-0000N.gguf` 形式，必须下载同组全部分片到一个目录，再选首片。至少预留权重体积、下载临时文件以及运行缓存所需空间。仅凭目录名无法辨认模型，入库后核对程序读取的 GGUF 名称、量化和上下文。
3. 默认先用 GGUF 内嵌聊天模板。若要复现本机曾验证的 Qwen 模板行为，从 [froggeric 模板仓库固定版本](https://huggingface.co/froggeric/Qwen-Fixed-Chat-Templates/tree/855bffc)下载 `chat_template.jinja`，在预设里选择「文件模板」并绑定它；模板与模型都需存在。不同版本必须重新测试。
4. 在「工作台」选择模型，打开能力/参数说明。新电脑先用较小上下文和 CPU/保守卸载量；原目标硬件可从下文 32K 档开始，仍需实测。点「启动」，等待**真实 API 就绪**，随后用「试聊」问一句简单问题，再做下文的工具闭环测试。试聊页的「单次生成上限（max_tokens）」可设为 8192；它是单次请求参数，不是模型原生能力。
5. 需要 DSH 时，按 [Node.js 官方页面](https://nodejs.org/en/download)与 [DeepSeek Harness 官方项目](https://github.com/deepseek-ai/deepseek-harness)安装当前受支持的组合。在「设置与诊断 → DSH 组件」选择安装目录和 `node.exe` 检测。进入「DSH 与提供方」，启动或连接已认证 DSH，连接本地 `/v1` API，选择模型，设为**新会话默认**，再开始 DSH 工作。

## 1. 先选运行方式

- **CPU 基线**：Windows x64、足够磁盘与内存即可先验证功能，但 27B 模型速度可能很慢，内存不足会加载失败。可以先选更小的 GGUF 练习流程。
- **NVIDIA GPU**：检查显卡驱动、显存和 [llama.cpp 发布页](https://github.com/ggml-org/llama.cpp/releases)列出的 CUDA 构建与配套 DLL。通常不必为预编译程序安装完整 CUDA Toolkit；不要把 CUDA 运行库 ZIP 与主程序 ZIP 混为一个文件直接选取。
- **AMD、Intel 等 GPU**：根据实际显卡、驱动与发布页选择支持的 Vulkan、ROCm 或其他构建。AMD 不等于一定可用 ROCm；没有把握时先用 CPU 版完成首次验证。伴航只检测所选引擎能力，不内置任何 GPU 后端。
- **空间**：下文三个现有示例文件约 11.77 GB、11.77 GB、14.40 GB；只下载自己要用的文件。下载时保留额外临时空间，运行时还要留操作系统、内存和显存余量。标称 262K 上下文是模型元数据上限，并不表示本机能运行 262K。

## 2. 获取并绑定 llama-server

从 [llama.cpp 官方发行页](https://github.com/ggml-org/llama.cpp/releases)下载与系统相符的 Windows 构建，**完整解压主包**。确认同一解压目录里有 `llama-server.exe` 与随包的 `llama*.dll`、`ggml*.dll` 等依赖；CUDA 构建若发行页另给 CUDA runtime 包，也按该页说明解压到正确位置。不要只复制一个 EXE。打开伴航「设置与诊断 → 运行环境」，选择 `llama-server.exe` 或其目录，然后「检测并使用」。能力下拉来自所选引擎 `--help` 和 GGUF 元数据；若某参数显示未知或不支持，换受支持的引擎或停用该参数，不能只看旧配方。

原机器留存的可用二进制文件名为 `llama-b11149-bin-win-cuda-12.4-x64.zip`，另有 `cudart-llama-bin-win-cuda-12.4-x64.zip`，这是**历史复现版本**，不是所有 GPU 的推荐版本。官方 [b11149 发行记录](https://github.com/ggml-org/llama.cpp/releases/tag/b11149)可用于核对版本。使用最新版时应重新做 API、模板和工具测试。

## 3. 选择正确模型仓库和文件

以下来源与现有文件名、GGUF 头部相符。`Qwen3.8-27B` 是模型系列；现有 GGUF 头部的架构字段为 `qwen35`，这是其内部架构标识，不能单靠目录名把它改叫另一个模型。

| 用途 | 来源仓库 | 现有量化文件示例 | 现有文件大小 |
|---|---|---|---:|
| 原版 GSQ-RCO | [ISTA-DASLab/Qwen3.8-27B-GSQ-RCO-GGUF](https://huggingface.co/ISTA-DASLab/Qwen3.8-27B-GSQ-RCO-GGUF/tree/main) | `Qwen3.8-27B-GSQ-RCO-IQ3_S.gguf` | 11,771,546,784 字节 |
| Huihui abliterated GSQ-RCO | [huihui-ai/Huihui-Qwen3.8-27B-abliterated-GGUF](https://huggingface.co/huihui-ai/Huihui-Qwen3.8-27B-abliterated-GGUF/tree/main) | `Huihui-Qwen3.8-27B-abliterated-GSQ-RCO-IQ3_S.gguf` | 11,771,546,208 字节 |
| Huihui 写作档 | [同一 Huihui 仓库](https://huggingface.co/huihui-ai/Huihui-Qwen3.8-27B-abliterated-GGUF/tree/main) | `Huihui-Qwen3.8-27B-abliterated-UD-IQ4_XS.gguf` | 14,403,496,864 字节 |

这些文件各自已经是 GGUF 量化成品，不需要再下载 `Qwen/Qwen3.8-27B` 全精度权重来“补齐”。若要选择其他量化，应先看仓库文件列表与自己的内存/显存，再下载那个**完整文件**。只下载几 KB 的 Git LFS 指针不是模型。分片模型需同组所有分片；不要混用不同量化、不同修订版。视觉能力还需与所选模型匹配的 `mmproj`，文本试聊无需下载它。下载中断后使用伴航的续传/校验状态；入库前确认文件大小与 GGUF 识别结果。

可选聊天模板的明确来源为 [froggeric/Qwen-Fixed-Chat-Templates](https://huggingface.co/froggeric/Qwen-Fixed-Chat-Templates/tree/855bffc) 的 v22.5、提交 `855bffc`。下载该修订的 `chat_template.jinja`，在「参数预设」选「文件模板」并绑定；启用 Jinja、DeepSeek reasoning format 等具体开关须以当前 `llama-server` 能力为准。只要 GGUF 已含聊天模板，也可先用「内嵌模板」建立基线。第三方模板属于可选组件，换版本后要重做工具调用测试。

## 4. 参数、启动与试聊

「模型库与下载」入库后在「工作台」选择模型；在「参数预设」查看能力读取结果和可选值。程序可给新模型建议的节省内存、均衡、质量档，但它们是**应用建议**，不是模型厂商保证可运行的硬件档位。先选较小上下文（如 4096 或 8192）、并发 1；GPU 层数可从低值逐步增加。参数保存前核对模型路径、所选模板以及引擎可用性。

旧目标硬件为 i7-13700K、RTX 4080 16 GB、64 GB RAM、Windows 11；旧环境还使用 llama.cpp b11149、上述模型及 froggeric v22.5。先在「设置与诊断」确认电脑身份与可用显存/内存；若发现是别的设备，停止按旧机器档位操作。以下档位只证明**原机器**的已记录结果：

| 档位 | 量化 | 上下文 | GPU 层 | 其余关键设置 |
|---|---|---:|---:|---|
| 原版或 Huihui 标准 | IQ3_S | 32768 | 60 | batch/ubatch 256，K/V q8_0，Flash Attention 开，并发 1；思考 medium、预算 4096 |
| Huihui 扩展 | IQ3_S | 65536 | 48 | 同上；内存压力更高 |
| Huihui 写作 | IQ4_XS | 8192 | 52 | 同上；需要更大权重空间 |
| Huihui 直接回答 | IQ3_S | 32768 | 60 | 思考 off、预算 0、温度 0.7；需模板及运行器支持 |

思考档常用温度 1.0、top-p 0.95、top-k 20、min-p 0、presence penalty 0；这是旧配方值，换模型或模板时重新判断。原始配方的思考设置为 `medium`、预算约 4096；原始“max generation 约 8192”是**请求输出上限**。在试聊页填 8192 只影响试聊请求；「DSH 与提供方」的「DSH 请求输出上限」留空时采用 `min(4096, 上下文/4)` 并受已知运行上限约束。若要让 DSH 请求尝试 8192，须在那里显式填写 8192，并由当前端点和上下文校验通过；不保证每次实际输出到 8192。参数预设 JSON 不保存这两个请求级字段。MTP 需保持关闭；普通预设没有打开它的字段。

启动后等待状态从进程存在进一步变成**API 已就绪**。在「试聊」输入“请用一句话说明你可以做什么”，看是否得到正文、思考内容是否按预期分离。要测试工具结构，可在隔离测试环境向 OpenAI 兼容 API 声明一个虚构 `get_weather` 工具，要求模型为“北京”给参数，核对 `tool_calls` 名称和 JSON 参数；接着把固定的虚构工具结果（如 `{"city":"北京","weather":"晴"}`）作为 tool 消息回传，确认模型继续给出基于该结果的回答。这个测试无需执行真实工具或写文件。单轮文本成功不能替代 tool result 闭环。

### 原始部署的十项完成条件

每项都要记录**本机**结果；旧报告和文件存在只算参考。可在独立目录复制已验证的引擎、模型和模板来避免重复下载，但复制后仍需重新绑定和测试。

| # | 怎么验收 | 完成标准 |
|---:|---|---|
| 1 | Huihui GSQ-RCO IQ3_S 发送中文问题 | API 返回有意义中文正文 |
| 2 | 切换到 Original GSQ-RCO IQ3_S 后发同题 | 实际切换模型并返回中文正文 |
| 3 | 给两版至少一题小型代码任务 | 代码与说明完整、可检查；记录失败 |
| 4 | 使用无副作用的虚构工具声明 | 响应含可解析工具名与 JSON 参数 |
| 5 | 回传固定虚构 tool result 再继续 | 模型正确引用结果并完成回答 |
| 6 | 停止服务后重新启动 | 旧端口释放、服务再达到 API 就绪 |
| 7 | 32K 稳定档 | 在接近目标长度的文档上完成检索/回答，记录用时、峰值 RAM/VRAM 与错误 |
| 8 | 内嵌模板与 froggeric 做 A/B | froggeric 思考正常退出、正文与 reasoning 分离、工具 JSON 完整；观察两者差异 |
| 9 | MTP OFF 基线 | 记录普通引擎未启用 MTP 的启动配置和上述结果 |
| 10 | 仅在隔离 sandbox 中让 DSH/Agent 做真实多步文件任务 | 授权范围限 sandbox；让 Agent 创建小文件、读取/修改、运行无害检查并汇报，核对最终文件内容与工具链路 |

十项未完成时只能报告“部分完成”。原始要求中的 64K、128K、262K、MTP A/B、视觉和 compaction 是稳定基线后的条件式实验，见《进阶实验路线.md》。

## 5. 安装并连接 DeepSeek Harness

从 [Node.js 官方下载页](https://nodejs.org/en/download)安装受支持的 Node.js，再按 [DSH 官方安装说明](https://github.com/deepseek-ai/deepseek-harness#run)安装或运行。DSH 是开发预览版，版本可能破坏兼容；不要盲目把旧配方中的版本当作永远最新。伴航当前预留的独立安装清单钉住 `@deepseek-ai/dsh` **0.1.5-rc.3**，应先在自己的环境确认该精确版本及其依赖可完整安装、启动、认证；若官方当前发行说明建议其他版本，以已验证的完整组合为准。Node 版本也应按官方当前要求和实际 `node -v` / DSH 启动结果确认，不能把任意插件加载错误直接归因于 Node。

在「设置与诊断 → DSH 组件」选择 DSH 安装目录与 `node.exe`，点检测。进入「DSH 与提供方」，可以启动本程序管理的 DSH；若连接外部 DSH，粘贴其**原启动认证链接**，只在本次会话中使用，不写入共享文档。随后用「将所选本地模型与预设接入 DSH」或手动新建本地提供方：Base URL 取伴航显示的本机 API 地址（通常形如 `http://127.0.0.1:<端口>/v1`），模型名用工作台所示 API alias，API 密钥用界面安全输入，并填写 GGUF 元数据及实际配置确认的上下文长度。先做「连接测试」，再设为「新会话默认」，最后点「开始 DSH 工作」。已打开的旧会话未必跟随新默认设置，应新建会话验证。只有本地模型 API 就绪、DSH 已认证、提供方连接成功，才把生成结果视作端到端通过。云端提供方可能产生费用，需另行配置，不在本流程中自动接入。

## 6. 局域网 API、退出与恢复

默认只用本机 API。要让同一局域网的其他设备访问，在伴航里开启「允许局域网访问 API」，设置有效 API 密钥，选择正确网卡显示的局域网地址，并按界面提示只对专用网络/本地子网放行模型端口。客户端使用屏幕显示的 `http://<局域网IP>:<端口>/v1`；`0.0.0.0` 是监听地址，不是客户端地址。用第二台设备分别测试**正确密钥成功、错误密钥和无密钥拒绝**，同时确认管理界面无法从局域网打开；本机访问自己的局域网 IP 不能代替跨设备测试。不要把 API 或 DSH 认证链接公开到互联网。

最小化到托盘会保留运行中的模型；窗口右上角 X 按当前版本策略停止本程序管理的模型并退出。开机启动管理器、启动后加载模型、启动收托盘是独立且默认关闭的选项。出现端口占用，先看占用进程与端口，不要结束未知程序；模型加载失败看伴航日志并降低上下文/GPU 层或换 CPU 引擎；模板工具结构异常时先切回 GGUF 内嵌模板做对照；DSH 插件错误应记录第一处原始错误和实际版本，检查安装完整性与官方已知问题。

「设置与诊断 → 网络代理」中的直连、系统代理、自定义 HTTP/HTTPS、SOCKS5 主要影响 Hugging Face 下载。伴航启动的 DSH 仅支持 HTTP/HTTPS 代理，改动后须重启 DSH；外部 DSH 需在它自己的环境设置。SOCKS5 不能直接用于伴航管理的 DSH。本机 API 与管理接口保持本地直连，代理应绕过 `localhost`、`127.0.0.1` 和本机局域网地址；否则可能出现模型已就绪而连接测试失败。

## 来源与复现边界

模型文件名、量化和大小来自上述 Hugging Face 仓库与原部署文件；GGUF 元数据确认架构 `qwen35`、量化 IQ3_S/IQ4_XS、标称 262144 上下文及内嵌聊天模板。旧部署报告记录了 b11149、froggeric v22.5 和特定硬件上的性能/工具测试，不能作为其他电脑的通过证明。伴航的管理预设、默认关闭自启动、局域网开关和退出行为是**应用策略**。官方参考：[Qwen 原模型卡](https://huggingface.co/Qwen/Qwen3.8-27B)、[llama.cpp 发行页](https://github.com/ggml-org/llama.cpp/releases)、[DSH 官方项目](https://github.com/deepseek-ai/deepseek-harness)。第三方下载和许可证请在各来源页阅读；本指南不分发这些程序或权重。
